## Non-Negotiable Invariants

1. **Continuous Doc API & OpenAPI Maintenance**: The [`.ai/doc-api.md`](.ai/doc-api.md) file and OpenAPI 3.1 specification (`api/openapi/openapi.yaml`) MUST be kept updated on **every code change or addition**, regardless of how small the modification is, if any endpoint, schema, proto, Kafka/Redis/ClickHouse contract, or metric is touched.
2. **Secured Logging**: All logging must be structured JSON (`structlog` / JSON `logging`). Strictly redact Kafka SASL/SCRAM credentials, Redis/ClickHouse passwords and DSNs, bearer tokens, raw chunk text, PII/PHI, and internal cluster paths before emission. Never use `print()` in `cmd/` or `internal/`.
3. **Partition Key Anchored to `trace_id`**: Consume from Kafka topic `rag-diagnostic-traces` (32 partitions) strictly partitioned by `hash(trace_id)` so all spans for a query execution tree land on the same worker subprocess for deterministic in-memory DAG assembly.
4. **Multi-Process `uvloop` & `jemalloc` Memory Discipline**: Run 3–4 dedicated worker subprocesses per pod matching CPU limits (`2,000m / 4,000m`), with `LD_PRELOAD=/usr/lib/x86_64-linux-gnu/libjemalloc.so` (`MALLOC_CONF=background_thread:true,dirty_decay_ms:1000,muzzy_decay_ms:2000`) to keep pod RSS strictly $\le 2.0\text{ GiB}$ under $\ge 12,000\text{ spans/sec}$.
5. **Bucketed Time-Wheel & Partial DAG Persistence**: Correlate out-of-order spans using a bucketed time-wheel ring buffer; on deadline expiration, tag incomplete DAGs with `is_partial = true` and flush surviving spans without null-pointer exceptions.
6. **Two-Tier ClickHouse Micro-Batching & Atomic Offset Commits**: Flush to ClickHouse via native TCP exclusively upon hitting `50,000` records or `2.0s` (whichever occurs first). Commit Kafka offsets **if and only after** ClickHouse confirms micro-batch writes to disk; on ClickHouse outage, pause offset advancement and spool to local disk WAL (`disk_wal.py`).
7. **Decoupled Evaluation Boundary**: Never call Temporal gRPC APIs or formulate evaluation prompt-context triplets on the worker; `rag-eval-worker` queries ClickHouse offline via scheduled pollers or materialized views.
8. **Code Cleanliness & Quality Gates**: All Python code must pass `ruff check`, `ruff format --check`, `mypy --strict`, `bandit`, `pip-audit`, and `pytest` suites.

## Git Commit Standards

- **Git Commit Frequency**: Commit code as you build. Every working session or phase must contain **at least two git commits**.
- **Conventional Commit Patterns**: All git commit messages must strictly adhere to the following prefixes:
  - `feat:` for new features 
  - `fix:` for bug fixes
  - `refactor:` for code refactoring
  - `docs:` for documentation updates
  - `tests:` for tests addition and modification
  - `chore:` for maintenance tasks and environment setup

## Pre-Commit Verification Rules

Before committing code, submitting changes, or marking a task complete:

1. Run formatting & linting: `ruff format --check .` and `ruff check .` (when Python source files exist).
2. Run strict type checking: `mypy --strict cmd internal` (when `cmd/` and `internal/` scaffolding exists; not required for documentation-only commits).
3. Run security & secured logging audit: `bandit -r cmd internal -ll -ii` (when `cmd/` and `internal/` scaffolding exists) and verify zero `print()` calls, credentials, DSNs, raw chunk text, or PII/PHI in logs.
4. Run test suites: `pytest test/unit -v` (when `test/unit/` scaffolding exists; not required for documentation-only commits).
5. Verify [`.ai/doc-api.md`](.ai/doc-api.md) and `api/openapi/openapi.yaml` are updated with all API, schema, proto, Kafka, Redis, ClickHouse, or metric contract modifications.
6. Update [`.ai/progress-tracker.md`](.ai/progress-tracker.md).
